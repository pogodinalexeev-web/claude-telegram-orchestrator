# Поиск по заметкам: как устроен и почему так

*Смысловой поиск по собственному хранилищу — то, что превращает бота из говорящей головы в ассистента, который помнит.*

---

## Задача

У человека полторы тысячи заметок за год. Он спрашивает: **«что мы решили по той истории с поставщиком?»**

Обычный поиск по словам тут бесполезен: в заметке написано «претензия», а спросили «конфликт»; написано «Иван из логистики», а спросили «перевозчик». Слова разные — смысл один.

Смысловой поиск решает именно это: находит по близости смысла, а не по совпадению букв.

---

## Из чего собрано

| Часть | Что делает |
|---|---|
| **Модель** `paraphrase-multilingual-MiniLM-L12-v2` | превращает кусок текста в 384 числа — «отпечаток смысла» |
| **`sqlite-vec`** | хранит отпечатки рядом с текстом, в одном файле базы |
| **`FTS5`** (встроен в SQLite) | полнотекстовый поиск по точным словам |
| **`RRF`** | сливает два списка результатов в один честный ранг |
| **Дежурный** | держит модель прогретой и векторы в памяти |

**Ни одного внешнего вызова.** Модель работает на процессоре, интернет нужен ровно один раз — скачать её. Заметки не покидают машину: для личного дневника это не мелочь, а условие задачи.

Модель взята в **сжатом виде (int8)** — 225 МБ вместо примерно гигабайта, качество поиска на глаз то же.

---

## Как это работает

### 1. Нарезка

Заметка режется по заголовкам, длинные секции добиваются по абзацам до 1600 знаков. Каждый кусок помнит, из какого файла и с какой строки он взят — поэтому в выдаче можно показать `файл:строка`, а не просто «где-то тут».

### 2. Индексация с диффом с обоих концов

Наивный способ — при каждой правке файла пересчитывать его целиком. Для дневника на 256 КБ это 110 кусков через нейросеть: минуты работы вентилятора на каждую дописанную строку.

Здесь иначе. При правке файла ядро сравнивает старую и новую нарезку **с начала и с конца**, находит общее начало и общий хвост и трогает только середину:

```
старое:  [A][B][C][D][E]
новое:   [A][B][X][D][E]
                 ↑ пересчитан только X
```

Хвосту при этом не пересчитываются векторы — ему **правится порядковый номер**. Двигаем числа вместо того, чтобы гонять нейросеть.

Почему это важно именно здесь: журналы принято вести **новым сверху**. Приписка в начало файла ломает наивный дифф по префиксу полностью — первый же кусок не совпадает, и пересчитывается всё. С двусторонним диффом приписка сверху стоит один кусок.

> **Замер.** Файл 256 КБ, 110 кусков, дописан блок в начало.
> Было: 110 кусков через модель. Стало: **1 кусок**.

### 3. Векторы матрицей в памяти

Отдельный поворот, который стоил половины скорости.

Изначально поиск читал векторы из базы на диске: движок `sqlite-vec` перебирал их сам. На свободной машине это давало приличные полсекунды — а под нагрузкой страницы базы вылетали из кэша операционной системы, и та же операция начинала стоить **2.7–4 секунды**.

Теперь все векторы держатся одной матрицей в оперативной памяти: 39 тысяч кусков × 384 числа = **около 60 МБ**. Поиск — это одно матричное умножение, десятки миллисекунд, диск не участвует.

> **Замер.** Векторная часть поиска: **2.7–4.0 с → 0.1–0.4 с**.

**Почему не векторная база и не ANN-индекс.** Соблазн взять faiss или hnswlib велик, но на наших объёмах это проигрыш:

- полный перебор 40 тысяч векторов — это чтение 60 МБ из памяти, то есть единицы миллисекунд; приближённый поиск экономил бы то, чего и так нет;
- ANN-индексы **деградируют от частых правок**: удаление помечает точку мёртвой, граф фрагментируется, лечится только периодической перестройкой. А у нас заметки меняются каждую минуту;
- лишняя зависимость, лишний формат на диске, лишний способ сломаться.

Порог, за которым ANN начинает окупаться, — сотни тысяч векторов. До него прямое умножение и быстрее, и проще.

### 4. Два поиска вместо одного

Смысловой поиск силён на расплывчатых вопросах и слаб на точных: имя файла, артикул, фамилия. Полнотекстовый — ровно наоборот.

Поэтому ищут оба, а результаты сливаются методом **обратного рангового слияния (RRF)**: каждый список даёт кандидату очки по его месту, очки складываются. Кусок, который нашли оба — наверху. Это заметно устойчивее, чем пытаться сравнивать «похожесть» с «релевантностью» напрямую: величины разной природы.

В выдаче каждый результат помечен, кто его нашёл: смыслом, словом или обоими.

### 5. Дежурный

Загрузка модели занимает около минуты. Платить эту минуту на каждый вопрос немыслимо, поэтому модель держит долгоживущий процесс — дежурный, слушающий unix-сокет.

Внутри — **две копии модели с разными ролями**:

- **поисковая**, на двух потоках, живёт всегда: её задача — ответить быстро;
- **индексирующая**, на пониженном приоритете, выгружается после 15 минут простоя: её задача — переварить новые заметки, никому не мешая.

Разделение появилось не от красоты: фоновая индексация забирала все потоки, и время поиска скакало от 1.7 до 6.5 секунды. С раздельными копиями — ровные 1.2–1.5 секунды полного цикла.

### 6. Один дежурный на машину, несколько хозяев

Схема «свой дежурный каждому» стоила 1.2–1.5 ГБ памяти **на человека**. Теперь дежурный один, модели общие, а у каждого хозяина свои:

- база и матрица векторов,
- **сокет с его правами `0600`**.

Изоляция сделана транспортом, а не проверкой внутри: чужой сокет невозможно открыть — не пустит ядро операционной системы. Маршрутизация идёт по тому, в какую дверь постучали, а не по полю в запросе — так не бывает путаницы при одновременных вопросах.

> **Замер.** Три хозяина: было ~3.9 ГБ (три дежурных), стало **0.9 ГБ** (один).
> Проверка изоляции: пользователь без прав пытается открыть чужой сокет — отказ.

## Свежесть: почему не нужно ждать индексации

Индекс дособирается **после каждого сообщения**, а не перед поиском. К моменту, когда вы что-то спрашиваете, пересчитывать уже нечего — поиск идёт сразу.

Досборка перед поиском осталась страховкой на случай правок с другой машины и обычно ничего не делает.

## Установка

```bash
# зависимости
python3 -m venv venv && ./venv/bin/pip install sqlite-vec fastembed onnxruntime

# машинная настройка — свой файл на каждой машине, вне git
cp search/localcfg.example.py search/localcfg.py && nano search/localcfg.py

# первая сборка индекса (долго: считает всё хранилище)
./venv/bin/python search/build_index.py

# поиск
./search/search "что там было про поставщика" 5
```

Выдача:

```
[поиск 0.31с]
1. [0.0316 С/Сл] Projects/Поставщики/log.md:212 › Итоги разговора
   Договорились: спорную партию меняют, срок — до пятницы...
```

`С` — нашёл смысл, `Сл` — нашло слово, `С/Сл` — оба. Оценка низкая (около 0.016 против 0.03 у хороших попаданий) означает, что модель сама не уверена: выдаче в этом случае доверять не стоит.

## Чему научила эксплуатация

**Мерить по частям до того, как чинить.** За одну ночь виновник медленного поиска дважды оказался не тем, кого подозревали: сначала грешили на перебор векторов, оказалось — на кодирование запроса; потом на кодирование, оказалось — на чтение с диска. Раздельные секундомеры на каждый участок пути сэкономили бы обе стройки.

**Заплатка, которая не работала.** Дифф по кускам был написан за сутки до того, как выяснилось, что он не срабатывает ни разу: порядок кусков в базе не совпадал с порядком в файле из-за кривой арифметики номеров строк. Код был, эффекта не было. Урок простой: правка без замера «до и после» — это надежда, а не инженерия.
